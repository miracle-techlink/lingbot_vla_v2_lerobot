{稠密即更快:小 Token 规模下稀疏 MoE 的双 GEMM 纯 PyTorch 实现}
{以 LingBot-VLA 2.0 动作专家为案例的测量、方法与前后对比实验}
{LingBot-VLA 加速工作组 \quad 测试平台:NVIDIA A100-SXM4-80GB \quad 代码分支 \texttt{lingbot-v2-accel}(基于 lerobot PR \#3967)}

\begin{cnabstract}
流匹配 VLA 策略的去噪循环把稀疏 MoE 专家置于一种极端工况:每次前向只有 51 个 token,却要经过 36 层 $\times$ 10 步共 360 次 MoE 调用。本文的测量表明,此时 MoE 的瓶颈既非 FLOPs 也非显存带宽,而是\textbf{kernel 发射开销与 torch.compile 图断裂}:A100 上 MoE 的真实 GPU 忙时仅 26.6 ms/次推理,墙钟却付出 300 ms 以上。据此我们把 top-$k$ 路由 MoE 重写为\textbf{两个普通稠密 GEMM}:将全部 32 个专家的 gate/up 权重按专家维拼接为单个矩阵,一次 GEMM 算出全部专家的中间激活;top-$k$ 路由权重 one-hot 化后直接折叠进中间激活,使第二个(down)GEMM 的归约天然完成``按权重合并专家''——未选中的专家权重恒为 0,因此与精确路由\textbf{代数等价}。该实现纯 PyTorch、静态形状、可微分,且可被 dynamo 整图追踪。A100 实测:推理(与 compile 联用)1489.1 $\to$ 398.5 ms(\textbf{-73.2\%});训练 $B{=}4$ 单步 2807.1 $\to$ 1501.3 ms(\textbf{-46.5\%});数值差异为浮点重结合级别(动作相对差 0.78\%,训练 loss 相对差 $9\times10^{-7}$)。在非编译回退路径上,稠密实现(228.4 ms)同样快于手写 Triton grouped-GEMM(365.7 ms)。
\end{cnabstract}
\keywords{Mixture-of-Experts;视觉-语言-动作模型;流匹配;kernel 发射开销;torch.compile;纯 PyTorch 算子}

\section{引言}
LingBot-VLA 2.0(lerobot PR \#3967)采用 pi0 式双流架构:Qwen3-VL-4B 作为视觉-语言骨干,并联一个 36 层、hidden 768 的 Qwen2 动作专家;动作通过流匹配(flow matching)生成,一次推理执行 10 步 Euler 去噪,每步将 51 个 suffix token(state 1 + action chunk 50)送过动作专家。动作专家的\textbf{全部 36 层}都是稀疏 MoE(32 专家、top-4 路由、专家中间维 512,另有共享专家 704)。

这意味着一次推理包含 $36 \times 10 = 360$ 次 MoE 前向,而每次前向仅 51 个 token、204 条路由。MoE 文献中的经典优化目标——大 batch 下的专家并行与显存容量——在此完全错位:单次调用的计算量只有约 0.48 GFLOP,A100 上纯 GEMM 时间以微秒计。本文要回答的问题是:\textbf{在这种``小 $T$、高频次''工况下,MoE 的正确实现形态是什么?}答案与直觉相反:把 32 个专家\textbf{全部稠密计算}再按权重丢弃,比精确路由更快——因为路由机制本身(argsort、gather、scatter、per-expert 启动)的成本已经超过了它省下的 FLOPs。

\section{方法}

\subsection{记号与常规实现}
设 token 数 $T$,隐藏维 $H$,专家数 $E$,专家中间维 $I$,top-$k$ 路由。输入 $X \in \mathbb{R}^{T\times H}$;专家 $e$ 的权重 $W_g^{(e)}, W_u^{(e)} \in \mathbb{R}^{I\times H}$,$W_d^{(e)} \in \mathbb{R}^{H\times I}$(\texttt{nn.Linear} 约定 $[\text{out},\text{in}]$)。路由给出选中专家集合 $\mathcal{S}(t)$ 与权重 $r_{t,e}$。常规输出:
\begin{equation}
Y_t = \sum_{e\in\mathcal{S}(t)} r_{t,e}\cdot \big[\, \mathrm{SiLU}(x_t W_g^{(e)\top}) \odot (x_t W_u^{(e)\top}) \,\big]\, W_d^{(e)\top}
\end{equation}
分组(grouped)实现先按专家排序 gather 出每专家的 token 块,再逐专家(或按专家的 grouped kernel)做三次小 GEMM,最后 scatter 回原位——这正是发射开销与图断裂的来源。

\subsection{权重打包与路由权重折叠}
构造两个 $E$ 主序的打包权重(推理时一次性缓存):
\begin{equation}
W_1 = [\,W_g \,;\, W_u\,] \ \text{按专家拼接} \to \mathbb{R}^{H \times E\cdot 2I},
\qquad
W_2 = W_d\ \text{按输入维拼接} \to \mathbb{R}^{E\cdot I \times H}
\end{equation}
前向只用两个普通 GEMM:
\begin{equation}
[\,G \,\|\, U\,] = X W_1 \in \mathbb{R}^{T\times E\cdot 2I}
\end{equation}
\begin{equation}
M = \mathrm{SiLU}(G)\odot U \in \mathbb{R}^{T\times E\times I}, \qquad \tilde{M} = M \odot R
\end{equation}
\begin{equation}
Y = \mathrm{reshape}(\tilde{M}, [T, E\cdot I]) \cdot W_2 \in \mathbb{R}^{T\times H}
\end{equation}
其中 $R \in \{0\}\cup\mathbb{R}^{T\times E}$ 是把 top-$k$ 权重 one-hot 回稠密路由表($e\notin\mathcal{S}(t)$ 处恰为 0)。式 (5) 的 GEMM 归约沿 $E\cdot I$ 维求和,自动完成式 (1) 中的 $\sum_e r_{t,e}(\cdot)$——\textbf{加权合并不需要任何 scatter/index\_add,它就是 down GEMM 本身}。

\subsection{等价性与数值}
未选中的专家 $r_{t,e}=0$,其贡献逐项为 0,故式 (5) $\equiv$ 式 (1),差异仅来自浮点重结合(bf16 GEMM 的累加顺序变化)。实测:fp32 下最大相对差 $1.4\times10^{-6}$,bf16 下 $4.8\times10^{-3}$(GPU),与 attention 后端切换造成的偏差同量级;端到端动作相对差 0.78\%,训练 seeded loss 相对差 $9\times10^{-7}$(见 \S 4)。

\subsection{复杂度与适用条件}
稠密化把专家 FLOPs 放大了 $E/k = 8$ 倍(每层 0.48 $\to$ 3.85 GFLOP)。代价成立的条件是``\textbf{发射成本 > 计算成本}''。本例中:路由机制(排序 + 32 路 gather/scatter + grouped kernel 的网格早退)约 15--20 次发射 $\times$ 360 次调用,而 8 倍 FLOPs 折算的 GPU 时间增量仅约 30--70 ms/次推理(A100,小 GEMM 效率按 20--40 TFLOPS 估)——且实测中这部分还被 GEMM 固定开销进一步吸收。门控阈值 \texttt{moe\_dense\_max\_tokens}(默认 512)刻画交叉点:$T \le$ 阈值走稠密,否则回退 grouped/eager 路径。注意``排序 + 定容 padding''方案在本工况下退化:容量上界 $\mathrm{cap} = T = 51$,pad 后的形状 $[32, 51, H]$ 与稠密全算完全相同——所以稠密是严格更简且同价的形态。

\subsection{与 torch.compile 的协同}
两个 matmul + 逐点运算,全程静态形状、无 \texttt{.item()}/\texttt{.tolist()}、无自定义内核——\texttt{fullgraph=True} 直接通过。去噪步的 36 层得以融合为一张图,这是 \S 4 中 compile 收益的主要成分。梯度路径同样成立:autograd 下不读权重缓存(每次现算打包,梯度正常回流到三个专家参数),训练同码复用。

\begin{lstlisting}[language=Python,caption={稠密双 GEMM MoE 核心前向(推理路径,缓存打包权重)},label=lst:dense]
w1, w2 = self._dense_packed_weights()   # [H, E*2I], [E*I, H]
gu = (hidden_states @ w1).view(T, E, 2 * I)
inter = F.silu(gu[..., :I]) * gu[..., I:]
w = torch.zeros(T, E, dtype=torch.float32, device=hidden_states.device)
w.scatter_(1, selected_experts, routing_weights.to(torch.float32))
inter = inter * w.unsqueeze(-1).to(inter.dtype)
return (inter.reshape(T, E * I) @ w2).to(hidden_states.dtype)
\end{lstlisting}

\section{讨论}
\begin{itemize}
\item \textbf{何时不该用稠密}:$T$ 很大(长序列训练、大批次)时 8 倍 FLOPs 成为真实算力开销,交叉点由 GEMM 效率与发射成本共同决定,故保留阈值开关与回退路径。
\item \textbf{与 CUDA graphs 的关系}:图完整后 launch 间隙进一步可用 CUDA graphs 消除,但本次工作按既定约束未使用;稠密实现与之正交、可叠加。
\item \textbf{社区可接受性}:实现不含任何专用内核,依赖为零增量,数值与原路径等价,满足 lerobot 的入库约束。
\item \textbf{局限}:表 2/3 测于 CPU 有负载的宿主机,空闲机绝对值会更低(before 空闲基线 1039.5 ms);编译范围目前仅覆盖 \texttt{predict\_velocity},vision/prefix 段的编译是下一步。
\end{itemize}

\section{结论}
在``小 $T$、高频次''的流匹配 VLA 工况下,稀疏 MoE 的最优实现不是更精巧的路由调度,而是把调度整个删掉:两个打包 GEMM + 权重折叠,在纯 PyTorch 内同时获得等价数值、整图可编译性与训练推理同码。这提示一类更普遍的判断:\textbf{当每层计算微秒级时,先数 kernel 发射次数,再谈 FLOPs。}
