\begin{cnabstract}
对 LingBot-VLA 2.0 部署链路的实测显示:模型推理本身经优化后已降至约 400 ms,而 \textbf{CPU 预处理管线在多相机配置下高达 $\sim$1 s,是模型耗时的 2.6 倍},且完全未被官方 130 ms 的延迟声明覆盖(该口径只计 \texttt{sample\_actions})。预处理随每次推理调用执行一次(每个动作 chunk 一次,而非每个控制步一次),在异步部署模式下,端到端延迟必须小于 chunk 覆盖的墙钟时间——当前 1.4 s 的端到端延迟已击穿 25 步 @ 30 Hz 的 833 ms 预算。本方案提出三项纯工程改造:① 图像管线整体 GPU 化(uint8 原图直接上卡,resize/归一化/patchify 用融合算子完成);② episode 级 tokenizer 缓存(task 字符串在 episode 内不变,每 chunk 重复 tokenize 纯属浪费);③ 预处理与去噪推理的跨 chunk 流水。预期端到端延迟进入 500 ms 以内,使异步模式下的高频控制成立。全部改动为纯 PyTorch/工程手段,不引入专用内核。
\end{cnabstract}
\keywords{数据预处理;GPU 卸载;tokenizer 缓存;流水线重叠;VLA 部署}

\section{执行频率与预算约束}
预处理不是每个控制步都跑,而是\textbf{随每次推理、每个动作 chunk 跑一次}:chunk 执行模式下,step 0 新观测 $\to$ 预处理 $\to$ 推理 $\to$ 50 步 chunk;step 1\dots24 直接执行 chunk,不推理不预处理;step 25 chunk 耗尽,重新进入下一轮。预处理每 chunk 一次,被 use\_length(25--50)个控制步摊薄。

是否需要优化,取决于部署模式的硬约束。异步重叠模式(执行当前 chunk 的同时计算下一个)要求:
\begin{equation}
T_{\mathrm{e2e}} = T_{\mathrm{preprocess}} + T_{\mathrm{model}} \;\le\; \text{use\_length} \,/\, f_{\mathrm{ctrl}}
\end{equation}

\section{成本结构:为什么 CPU 管线慢}
对官方 \texttt{\_prepare\_model\_input} $\to$ \texttt{FeatureTransform.apply} $\to$ \texttt{prepare\_images} 链路的代码审查给出预处理的三个成本来源:
\begin{itemize}
\item \textbf{全数组遍历 $\times$ 单线程带宽。}每路相机从 uint8 原图到 patch 张量要经历约 6 次完整数组遍历:类型转换、torchvision Resize(256$\times$256)、Qwen3-VL image processor 的 smart\_resize、rescale、normalize、pad/patchify。每次遍历都新分配数 MB 的 numpy 数组,三相机再乘 3,外层还有 per-camera 的 Python 循环。
\item \textbf{数据传输方向颠倒。}现状是``CPU 处理完 $\to$ fp32 大张量最后才 \texttt{.to(device)}'';正确方向是``uint8 原图(3 路共 2.8 MB)直接 pinned + 异步 H2D($<$0.5 ms)$\to$ 处理全程在卡上''。
\item \textbf{与推理的 launch 线程抢 CPU。}该模型推理是 launch-bound(GPU 忙时仅 $\sim$225 ms/次),CPU 时间极其宝贵;预处理独占 CPU $\sim$1 s,直接拖慢两侧的 kernel 发射——宿主机有负载时预处理从 $\sim$300 ms 恶化到 1023 ms 即为此机制。
\end{itemize}
tokenizer 一项是次要成本:task 字符串整个 episode 不变,却每 chunk 重新渲染 chat template(含数百个 image\_pad 占位符)、重新编码,单次约数 ms——收益小但实现几乎免费。

\section{方案设计}

\subsection{图像管线 GPU 化(主收益项)}
将每相机的``转换 $\to$ resize $\to$ 归一化 $\to$ patchify''从 numpy/PIL 改为卡上融合算子,并把多相机从 Python 循环改为单次批量调用:
\begin{lstlisting}[language=Python,caption={图像管线 GPU 化示意}]
# 现状(每相机,CPU):uint8 -> float32 -> Resize -> smart_resize -> rescale -> normalize -> patchify
# 方案(所有相机,GPU):
imgs = torch.from_numpy(np.stack(frames))         # [Ncam, H, W, 3] uint8
imgs = imgs.pin_memory().to("cuda", non_blocking=True)
x = imgs.permute(0, 3, 1, 2).float()              # 融合进后续算子
x = F.interpolate(x, size=(Hs, Ws), mode="bilinear", align_corners=False)  # == smart_resize
x = (x * rescale - mean) / std                    # 广播逐点,可与 patchify 融合
patches = rearrange(x, ...)                       # temporal/spatial merge 即 reshape/permute
\end{lstlisting}
\begin{itemize}
\item 数学上与 HF processor 逐步对齐(双线性 resize 参数、均值方差、padding 规则),以单元测试锁定逐元素等价;
\item 输出直接位于 GPU,下游 vision tower 零拷贝消费;
\item 多相机 stack 成 batch 维,一次 kernel 覆盖全部视角。
\end{itemize}

\subsection{episode 级 tokenizer 缓存}
在 deploy 包装层以(task 字符串, 图像 token 数)为键缓存 \texttt{lang\_tokens} 与 \texttt{lang\_masks}:episode 首次推理时计算,后续 chunk 直接复用。键含 image\_token\_count 是因为 Qwen3-VL 的 chat template 会把图像占位符展开进 prompt——图像分辨率不变时展开结果亦不变。预期收益数 ms 级,实现成本极低,顺手完成。

\subsection{跨 chunk 流水(部署侧,可选)}
异步模式下,下一观测的图像预处理与当前 chunk 的去噪推理天然可重叠:预处理线程在 GPU 空闲间隙提交 H2D 与图像 kernel,推理线程持续发射去噪 kernel。由于去噪是 launch-bound(GPU 留有 $\sim$70\% 空隙),两者的 GPU 资源几乎不冲突。此项无需改动模型代码,属部署编排。

\subsection{FeatureTransform 向量化(收尾项)}
55 维 canonical 槽位的拼接/归一化目前是 Python 循环;可预生成索引向量与 mean/std 常量,用一次 \texttt{index\_select} + 融合归一化替代。量级小(ms 级),在 4.1 完成后顺手处理。

\section{风险与兼容性}
\begin{itemize}
\item \textbf{resize 数值对齐}:HF smart\_resize 含取整规则(28 的倍数网格),双线性采样的边界行为需与 PIL/numpy 实现对齐——以逐元素测试锁定,差异超差时回退 CPU 路径;
\item \textbf{lerobot 处理器契约}:改动封装在 lingbot\_vla\_v2 自己的 processor 内,\texttt{PolicyProcessorPipeline} 框架不动;\texttt{device\_processor} 提前后需保证后续步骤对 CUDA tensor 兼容;
\item \textbf{回退路径}:无 GPU / 调试场景保留现有 CPU 管线,以开关切换。
\end{itemize}
